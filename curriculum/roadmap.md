# Kotlin 10주 로드맵

> Java/Spring 백엔드 개발자가 **"Kotlin을 쓴다"에서 "Kotlin 코드 품질을 검토하고 개선을 제안한다"로** 넘어가는 10주.

## 전제

| | |
|---|---|
| 학습량 | **하루 2~3시간 × 주 5일** = 하루 1레슨 + 주간 미션 진척 |
| 분량 | **50레슨 / 10주** (주 5레슨) |

| 도구 | `kotlinc 2.4.10 (JRE 21)`, 학습 서버(`node server.ts`, :3838), IntelliJ |

## 설계 원칙

**1. 언어를 빠짐없이 덮는다.**
이전 버전은 "Java 개발자가 놀라는 지점"만 골라 담아서 `when`·`companion object`·생성자 같은 기본이 빠졌다. 이번엔 **기초 문법부터 순서대로** 간다. 대신 설명 방식은 그대로 **Java 코드와 대조**한다.

**2. 표준 라이브러리는 "전수"로 훑는다.**
리뷰어가 되려면 **뭐가 이미 있는지 알아야** 한다. 스코프 함수 5개를 정밀하게 구분하고(Part 3), 컬렉션 API를 세 레슨에 나눠 훑는다. "그거 `groupBy` 로 한 줄입니다"라고 말하려면 `groupBy` 를 알아야 한다.

**3. 안티패턴을 명시적으로 배운다.**
매 레슨에 **리뷰 관점** 절이 있다. Part 4는 아예 코드 품질에 통째로 할애한다 — 관용구 판별(L29), 컨벤션·ktlint·detekt·리뷰 체크리스트(L30).

**4. 매일 손으로 친다.**
레슨마다 연습이 있고 기대 출력과 대조 채점된다. 막히면 힌트 4단계, 그래도 막히면 정답. 읽고 끄덕이는 건 학습이 아니다.

**5. 10주 끝에 이력서에 쓸 게 남는다.**
졸업 과제(L50)는 연습이 아니라 포트폴리오다.

## 면접관 시점 코멘트

5년차에게 "Kotlin 문법 아세요?"라고 묻는 면접관은 없다. 묻는 건 이거다.

> "왜 Java 대신 Kotlin을 썼나요? 팀 러닝커브 비용을 감수할 만한 이유가 뭐였죠?"

"간결해서요"라고 답하면 거기서 끝난다. 10주 뒤에는 이렇게 답할 수 있어야 한다 —

**"런타임 NPE를 컴파일 타임으로 당겼고, sealed class로 상태 분기 누락을 컴파일러가 잡게 했고, 코루틴으로 스레드풀 고갈 없이 I/O 병렬성을 확보했습니다. 대신 allOpen 플러그인 같은 Spring 연동 함정이 있어서 초기에 이런 사고가 있었고 이렇게 잡았습니다. 팀에는 detekt 규칙을 CI 게이트로 걸어서 Java 스타일 코드가 섞이는 걸 막았고요."**

마지막 문장이 이번 커리큘럼이 추가로 노리는 지점이다. **언어를 아는 사람과 팀의 코드 품질을 책임지는 사람은 다르게 보인다.**
